## 1. Executive summary
FlapTaxTokenV3 is a Flap-launchpad ERC20 tax token. It has a fixed 1B supply minted at initialize, asymmetric buy/sell tax that applies only after migration and only for a set duration, and an anti-farmer phase that taxes every registered pool. Accrued tax is liquidated through an external TaxProcessor, and a liquidation threshold adjusts in both directions. This run reviewed the verified source for every external entrypoint and diffed all 20 vendored OpenZeppelin files against the genuine npm releases. It found no reachable path that lets an unprivileged party steal funds, mint, seize ownership or freeze holders. Every remaining risk runs through parameters and contracts the launchpad sets at `initialize`: tax rates, `taxProcessor`, `dividendContract`, and the owner who triggers migration.

## 3. Methodology
The audit was threat-model-first. I derived 7 invariants (S5.0) and hunted for a path that breaks each one (S5). Every candidate went through adversarial refutation (S6). No finding survived, so the fuzzer did not run.
- Tools: slither(compile-fail), agentic(ok), fuzz(N/A: clean audit, hard gate)
- Slither compile-fail cause: crytic-compile used the Foundry platform and could not resolve the `@openzeppelin-contracts-upgradeable/` remaps against the materialized layout. I made one attempt and did not retry, per S3.
- Provenance: 20/20 vendored files are IDENTICAL by SHA-256 to `@openzeppelin/contracts-upgradeable@4.9.6` (16 files) and `@openzeppelin/contracts@4.9.6` (4 files). Nothing is DIFFERENT or UNVERIFIED. The only non-standard text is an advertising banner comment at the top of `FlapTaxTokenV3.sol` ("Bundle on Pons! … ignitr.io"). It has no effect on the code, but it suggests this deployment is a third-party (Ignitr/Pons) redeploy of Flap's V3 token on Robinhood Chain, not a Flap-team deployment.
- Constructor immutables decoded: `MIN_LIQ_THRESHOLD` = 50,000 tokens and `START_LIQ_THRESHOLD` = 400,000 tokens. MIN < START, so the threshold band is consistent.

## 4. Threat model and invariants
Actors: **anyone** can transfer, approve and permit. **owner** is whoever called `initialize` (the launchpad) and can only call startMigration and finalizeMigration, plus Ownable transfer/renounce. **taxProcessor** is trusted at init: it gets a max allowance on the token's own tax balance and returns the threshold direction. **dividendContract** is trusted at init: `setShare` is called on every holder transfer, and a revert there reverts the transfer. **pools** are fixed at init and decide whether a transfer counts as a buy or a sell.

| ID | Invariant | Why it matters |
|----|-----------|----------------|
| INV1 | totalSupply == 1e9 ether, minted once in initialize; no other mint path | Prevents inflation |
| INV2 | The implementation can never be initialized, and each clone initializes exactly once | Prevents takeover |
| INV3 | No tax is charged and no nested liquidation runs while `notLiquidating == false` | Prevents reentrancy / double-tax |
| INV4 | liquidationThreshold stays within [MIN_LIQ_THRESHOLD, initialLiquidationThreshold] | Prevents a liquidation DoS or dump |
| INV5 | owner cannot change balances, tax rates, pools or processors after init | Prevents admin rug |
| INV6 | tax <= amount for every taxed transfer | Prevents sell/buy bricking |
| INV7 | An unprivileged party cannot block another holder's transfers | Prevents freezing |

## 5. Findings
No confirmed findings.

### Candidates raised and refuted
- C1 (high-if-real, reentrancy): `_liquidateTax` makes an external call to `taxProcessor.processTaxTokens` in the middle of a user's transfer. **Refuted:** `notLiquidating` is set false and stored before the call. Nested `_transfer`s then skip liquidation and `_getTaxWithPoolState` returns 0. The outer transfer reloads `poolState` after the call. The processor is a trusted, init-set contract (INV3 holds).
- C2 (high-if-real, arithmetic): `buyTaxRate`/`sellTaxRate` are uint16, so values up to 65535 bps (>100%) are possible. Then `amount - tax` underflows and the transfer reverts, making the token unsellable or unbuyable. **Refuted as a privileged config:** the rates come only from `initialize` (launchpad) and have no setter. No unprivileged path reaches it. This is still a real per-clone *trust* check for holders (INV6); see §6.
- C3 (medium-if-real, DoS): `_afterTokenTransfer` reverts the whole transfer if `dividendContract.setShare` reverts, so a holder could be frozen. **Refuted:** `dividendContract` is set once by the launchpad and cannot be changed by users. Freezing requires control of a trusted contract (privilege >= impact).
- C4 (medium-if-real, access-control/lifecycle): if the owner never calls startMigration, or renounces during BondingCurve, pool transfers stay banned forever. **Refuted:** owner-only and intended launchpad lifecycle (privilege >= impact).
- C5 (medium-if-real, economic/MEV): anyone can force a tax liquidation by sending dust to `mainPool` once the balance reaches the threshold, then race or sandwich it. **Refuted:** the attacker cannot extract value atomically from the token contract. Slippage is bounded by `liqExpectedOutputAmount` inside the out-of-scope TaxProcessor. This is standard tax-token behavior.
- C6 (low, logic): the TaxEnforcedAntiFarmer → TaxEnforced → TaxFree transitions only happen on a transfer *to mainPool*. Buys made after the expiry but before the next sell are still taxed. **Not a vulnerability:** a bounded timing inaccuracy with no attacker gain. Recorded as informational.
- C7 (initializer): the implementation could be hijacked if uninitialized. **Refuted on-chain:** `_disableInitializers` ran in the constructor, and storage slot 0 = `0xff` (INV2).
- C8 (threshold band): MIN > START would invert the "decrease" signal. **Refuted:** decoded constructor args are MIN 50k < START 400k (INV4).

## 6. Coverage and limitations
- Explored: access control, reentrancy (single/cross-function, external callbacks), oracle/price (none on-token), arithmetic/precision (bps math, uint96/uint64/uint48 packing, timestamp casts), upgradeability (EIP-1167 clone implementation, initializer lock), external-call assumptions (try/catch on processor, revert-propagating dividend hook), signatures (OZ 4.9.6 ERC20Permit with EIP-712 chainId and nonces), economic/MEV (forced liquidation, LP-add during liquidation). The v4-hook checklist does not apply.
- Not exercised: Slither (compile-fail), fuzzing (clean-audit hard gate), the TaxProcessor/Dividend/factory code, and per-clone init params.
- Holder-facing note (not a finding): because tax rates are fixed at init with no upper bound check, a launchpad or bundler could ship a clone with `sellTaxRate` ≥ 10000, which makes the token unsellable. Similar dynamic-tax honeypots were reported on Flap's BSC launchpad. Check each clone's `sellTaxRate()` before trusting it.
- Honest partiality: a paid audit would also cover the TaxProcessor swap and slippage logic, the Dividend accounting, and the factory's init-parameter validation. That is where the remaining risk sits.
